Operator guide

Know what each step changes before you approve it.

Alpha software — evaluate before use

Bugs, security issues, and breaking changes can cause downtime, data loss, or missed rewards. Start with a disposable identity. Keep independent, tested backups before adopting an important node. Open source and valid signatures are not a guarantee of safety.

Before you start

QuilNode is the Mac management app. The Quilibrium node is a separate background service; qclient is its separately managed companion. Installing the app does not itself install a node or create an identity.

  • App compatibility: Apple Silicon and macOS 14 or later. Intel Macs, Windows, and Linux cannot run this app.
  • Node capacity: allow enough memory, SSD space, and reliable connectivity for the workload. Check the current Quilibrium requirements; passing the app's initial checks is not a capacity guarantee.
  • Permissions: a macOS administrator approves installation of the local service. Ordinary monitoring does not need a password.
  • Tools: the signed-node installation path does not need Xcode, Homebrew, Rust, or Cargo. Source-development builds have separate toolchain requirements.

Read the security model yourself or with a reviewer you trust. QuilNode is independent of, and not endorsed or supported by, Quilibrium Inc. or the protocol maintainers.

Download & verify

  1. Use the download page or quilnode/quilnode Releases. Read that release's compatibility notes and known issues. “Available soon” means there is no matching published installer; do not substitute a rehearsal build or a file from chat.
  2. Download the .dmg and SHA256SUMS from the same release. Keep the original filenames. Compare the DMG's SHA-256 with its exact entry in the checksum file. 
shasum -a 256 "/path/to/the-downloaded-file.dmg"

Replace the quoted path with your downloaded file. This command only reads the file. A mismatch means stop; do not open it. Matching a checksum downloaded alongside a file detects mismatched bytes, but does not independently authenticate the publisher.

Full signature and package verification

Technical reviewers can use the verifier from the reviewed source at the release's exact signed tag. Download every attached release asset into one otherwise empty directory; do not include GitHub's automatically generated source archives. From that source checkout, run: 

scripts/release/verify-release.sh "/path/to/release-assets"

The verifier uses the checked-in public keys to authenticate the signed report, feed, and DMG before mounting it read-only, then checks the delivered app and inventory. It needs the verifier's development tools, including Swift and Python 3; it does not need private keys and does not install the app. Review the source and trust anchors first. Do not add --rehearsal when verifying a public release.

Install & first open

  1. Open the verified DMG in Finder.
  2. Drag QuilNode onto the Applications folder link. Wait for the copy to finish, then eject the DMG.
  3. Open QuilNode from Applications, not from the mounted installer. The local service expects the installed app at /Applications/QuilNode.app.

When macOS blocks an unknown developer

Community-signed builds use the project's signing certificate. They are not Apple Developer ID signed or Apple-notarized. A valid project signature does not make the publisher Apple-verified.

If you have reviewed the source and release, verified the download, and choose to proceed:

  1. Try opening the installed app once.
  2. Open System Settings → Privacy & Security. Find the message about QuilNode and choose Open Anyway, if macOS offers it.
  3. Read the confirmation and authenticate if requested. Return to Applications and open QuilNode.

This is a specific app exception—not a reason to disable Gatekeeper. Stop if macOS says the app is damaged, contains malware, or will harm your computer. Do not run blanket quarantine-removal commands. See Apple's first-open guidance; managed Macs may require your administrator's help.

Set up your node

A new installation

  1. Let QuilNode setup inspect this Mac. Resolve blocked checks; do not treat “checking” as “offline.”
  2. Choose Acquire signed release. The app downloads and verifies the official node artifacts before offering installation.
  3. Read Review authorization and continue to the macOS prompt. The local service creates a restricted runtime account, installs the managed runtime, and configures its startup service and required operating-system limits.
  4. Wait for runtime validation. QuilNode installs or reuses a compatible managed qclient; do not install an unrelated copy into the app bundle.
  5. Choose an identity, make a separate recovery backup, then complete network readiness. A running process is not proof of enrollment or rewards.

Keep, import, or create an identity

  • Keep detected identity: retain the existing complete keyset and create managed rollback protection. If QuilNode does not detect an installation you expect, stop and review its location; do not create a replacement identity as a workaround.
  • Import an existing keyset: select the folder containing both config.yml and keys.yml. Never mix files from different backups. The local service checks the package and detects its format before activation.
  • Create a new identity: generate a new local identity with the verified runtime and client. A new identity does not inherit an old identity's seniority.

For legacy, including pre-.25, packages, keep an untouched copy before migration. Review the detected format and transaction plan. The installed runtime performs the required migration; do not hand-edit private-key fields. A changed network identity does not by itself prove loss of legacy identity continuity, and preserving files does not guarantee a particular chain seniority.

What the password authorizes

The macOS authorization prompt approves a restricted local service; QuilNode does not save your password. Routine authorized controls and signed updates can reuse that trust. Identity creation, import, activation, and recovery export deliberately require fresh approval. Changing the trusted app identity, repairing the service, or enabling a broader development-update policy can require another prompt. There is no promise of “one password forever.”

Cancel any unexpected prompt and review the operation first. No part of this setup requires disabling system protections or granting blanket Full Disk Access.

Network readiness

Open Network and follow its inbound setup. Use the plan generated from your current configuration, not port numbers copied from another operator. Revisit the plan after changing ports, workers, routers, or networks.

  1. Verify listeners. Keep the defaults unless you need a custom profile. Use Check now to confirm that the installed node owns the expected listeners.
  2. Review the macOS firewall operation. It can enable the Application Firewall and allow the installed node binary while preserving other rules. This does not configure your router or prove internet reachability.
  3. Configure your router manually. Use Copy plan, reserve the Mac's local address in the router, and forward only the listed node ports and transports to that address. Never expose local RPC, metrics, or management interfaces. Do not use a DMZ or forward every port.
  4. Check inbound evidence. An outbound peer connection is not proof that peers can initiate a connection to you. “Inbound traffic observed” is useful evidence; no observed traffic yet is not, by itself, proof of a blocked router.

Open detected gateway page uses the Mac's current routing information. It is a starting point, not a guarantee that the gateway has a web administration page. VPNs, multiple routers, or carrier-grade NAT can require help from the router vendor or ISP. QuilNode does not need your router password.

Keep macOS and router firmware updated. Opening node ports exposes the node software to unsolicited internet traffic; a firewall rule does not make that software vulnerability-free. See the official node networking guidance for protocol requirements.

App & node updates

These are two separate update systems. The App build version belongs to QuilNode. The Installed runtime version belongs to the Quilibrium node. Changing one does not mean the other changed.

Update the QuilNode app

  1. Finish or safely cancel any active node build, installation, or identity operation first.
  2. Open Updates → App build → Check app. Read the offered release notes and approve installation if you want it. The updater verifies the signed feed and update archive before replacing the application.
  3. Let QuilNode relaunch, then check the app version and local node status. The node runs as a separate service; an app replacement is not a node restart or a node upgrade.

Automatic app checks do not mean automatic installation: you approve each app replacement. If the feed is unavailable, that is not evidence that you are up to date. You can use a verified DMG from the same project's Releases page and follow the installation steps to replace the app. Do not run two copies or launch it from the DMG. Review any macOS warning; a future update is not guaranteed to be prompt-free.

Choose a node update policy

In Updates, use the Automatic channel selector and review its confirmation. These policies apply to the node, not QuilNode:

  • Manual: you initiate each node update. Use this if you want to review every change before it runs.
  • Signed Stable: automatically follows eligible official signed releases, with digest and signature-quorum verification. This is the most conservative automatic channel, not a guarantee that a release has no bugs.
  • Approved Dev: builds the exact upstream commit that changes the subpatch marker. “Approved” means marked for a development build; it is not the signed-release assurance level or a security certification.
  • Raw Dev: follows eligible upstream branch heads without requiring the approval marker. Experimental changes can fail to build or break compatibility. Use only if you accept that risk.

Source channels may need the build toolchain. Review the tool setup before authorizing it and allow enough time, memory, and disk space. A compatible, verified qclient is reused; it is acquired or rebuilt when the selected runtime requires it.

What to expect during an update

Preparation downloads or compiles the candidate while the current node stays running. Activation briefly stops it, switches the runtime, starts it again, and checks local health. A prepared candidate is not an installed update: wait for the completion receipt and verify Installed runtime.

Closing the dashboard leaves the menu-bar app running. Fully quitting QuilNode stops its update scheduler; a build is not a guaranteed background job after Quit. Keep the app open and the Mac awake during an operation. After interruption, reopen Updates and review the recovered receipt rather than starting a second build or assuming completion.

An automatic update has not started
  1. Confirm the selected channel, its authorization status, and the next-check information. Checks are periodic, not an instant push service; offline periods and upstream failures can delay them.
  2. If shown, use Retry automatic setup to review and repair authorization. A selected policy alone does not prove the local service accepted it.
  3. Read the last failure and build output. Automatic retries for an already failed candidate pause until a new upstream signal or a manual retry, avoiding repeated failed builds.
  4. Once the cause is addressed, use Run selected channel now, or Install staged update when a verified candidate is retained. Do not delete caches or stores merely because an update is waiting.

Backups & recovery

A node identity package is the matching config.yml and keys.yml pair. Treat both as secret. An address, peer ID, screenshot, or chain record cannot replace missing private keys.

Automatic rollback protects a local identity transaction. A Separate backup protects against losing this Mac. Runtime rollback in Updates protects the executable switch. None is a substitute for the others, and an identity export is not a full backup of node stores or app data.

Create a separate backup

  1. Open Recovery and confirm the active package. If it is not yet managed, use Protect identity first. Then choose Create backup or Create another copy.
  2. Choose a destination on encrypted storage you control, ideally separate from the Mac. Select the mounted encrypted drive or disk image and use Save Verified Recovery Copy. Review and approve the macOS authorization prompt.
  3. Wait for successful verification. Keep the entire exported folder together: config.yml, keys.yml, and RECOVERY.txt. Follow its recovery notes. Do not paste these files into chat, email, an issue, or an AI tool.
  4. Eject encrypted storage when finished and keep the unlock password or recovery material securely and separately. Retain untouched pre-migration copies and make a fresh backup after a successful migration or identity change.

Verified does not mean encrypted. QuilNode verifies the exported bytes and restricts local permissions; it does not encrypt the recovery folder. The destination must supply that protection. “Separate backup” records a successful export, not a current check of the media, its encryption, or a successful restore. Test your recovery procedure before relying on it.

Prepare encrypted storage without erasing a disk

Disk Utility can create a new encrypted, read/write disk image for your backup. Use Apple's secure disk image instructions. Select encryption before exporting, mount the image, and choose a folder inside it. An image kept only on this Mac does not protect against losing this Mac; keep an independent copy.

You do not need to erase or reformat an existing drive. Never erase storage that contains your only copy. Check that the image can be unlocked and read, and store its password safely: losing that password can make the backup inaccessible. Eject the image when not in use; mounted storage remains accessible to processes with permission to read it.

Restore or switch an identity

  1. Preserve the existing identity and its independent backup. Stop any other node using the identity you intend to activate; do not run duplicate copies of that identity to test recovery.
  2. In Recovery, choose Import identity package and select the complete backup folder. Review the detected format, public identity metadata, warnings, and transaction plan. Stop if the package is incomplete or not the identity you expected.
  3. Review the activation confirmation. For an already stored inactive package, select it and choose Switch & verify. The operation needs fresh authorization and a node restart. Do not interrupt it.
  4. Wait for validation, then confirm the active identity, node health, and backup coverage. Keep the old package until recovery is verified. Chain enrollment, allocations, and rewards may still need time or protocol progress after local startup.

Rehearse recovery in an isolated environment using a disposable identity. Do not wipe stores to restore keys: stores contain protocol state, not a replacement for your identity backup. A store reset or runtime downgrade can have protocol consequences; review current release guidance and diagnostics first.

Security & privacy

The graphical app passes selected folder paths and requests to a restricted local service. It does not read, display, copy, or send private-key bytes. The local service and official runtime do access identity material for authorized creation, backup, migration, and activation. Self-custody means those secrets stay under your control; it does not make a compromised Mac safe.

  • Keep macOS, QuilNode, and the node current. Review changes before widening an update policy or granting a new permission.
  • Do not grant blanket Full Disk Access, disable Gatekeeper, or weaken file permissions to clear an error. Cancel unexpected password prompts and inspect the operation first.
  • Use Privacy Mode around other people and before sharing a view, but inspect the result yourself. It masks classified values; it does not encrypt files, anonymize network traffic, or make clipboard contents and browser destinations private.
  • Never share real keysets, recovery folders, passwords, or signing material. Avoid publishing full node logs, local paths, addresses, and operational identifiers. Use disposable test data for reproductions.

QuilNode has no account, telemetry collector, or remote-command endpoint. Monitoring reads the local node. Release checks and downloads contact external distribution services, which receive normal network request metadata; local-first is not a promise of no internet traffic. This website uses Vercel Web Analytics for anonymized, cookie-free page-view metrics. It sends no custom events and receives no node, wallet, or application data. Read the privacy policy and security policy for the boundaries and reporting procedure.

When something fails

Start with Diagnostics, read the evidence and proposed action, and approve only the scoped repair you understand. A failed check is not permission to delete stores, replace an identity, or disable a macOS protection.

Frames or rewards are not progressing

Review local process health, archive connectivity, and protocol waiting states before restarting. An upstream archive or protocol delay can require waiting rather than a local repair. Healthy workers, active allocations, and observed proving do not by themselves prove credited rewards. Check the separate reward evidence and its freshness.

An update failed or stopped partway through

Open Updates and expand the build output or recovered receipt. Identify the failed step and whether activation started. An error during preparation does not mean the running binary was replaced. After an activation error, verify the actual running version and rollback outcome before retrying. A retained candidate can be installed only when the app offers that action. Do not treat a commit count or completed download as proof of a successful installation.

A backup folder reports permission denied

Protected managed folders are not intended for direct editing, even by an administrator. Export a separate copy through Recovery instead of changing ownership or making files world-readable. If export fails, preserve the original package and review the error; do not delete it or paste its contents into a support request.

I closed or removed the app, but the node is still running

The background node service is independent of the dashboard. Closing its window, quitting QuilNode, or deleting the app does not uninstall or stop that service. Use the app's node Stop control and verify the stopped state if you intend to halt it. Preserve and verify independent backups before removing any installation data; do not delete managed system folders by hand.

Report a bug or a security issue

For a non-security bug, open a GitHub issue with the app version, macOS version, reproduction steps, and expected versus actual behavior. Share only a reviewed, sanitized excerpt or disposable reproduction—not full logs or real node configuration.

For a suspected vulnerability, use Security → Advisories → Report a vulnerability when the private form is enabled. If it is unavailable, open a contact-only issue titled Security contact request asking for a private reporting channel. Include no vulnerability details, logs, screenshots, or attachments in that public request. Never send real private keys, even in a private report. See GitHub's private-reporting guidance.
